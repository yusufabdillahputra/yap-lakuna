# Lakuna · Flutter + Serverpod

Lakuna adalah aplikasi kasir (POS) offline-first untuk UMKM Indonesia (mode
Retail dan F&B). Read `CLAUDE.md` first: it holds the project rules (in
Bahasa Indonesia) and wins over anything below. Architecture and conventions
are in `docs/superpowers/specs/2026-11-03-f0-fondasi-arsitektur-design.md`.

Quick map:

- `lakuna_server`: Serverpod server. The `.spy.yaml` models under
  `lib/src/<area>/` are the single schema source for the on-device SQLite
  database (`database: all` / `database: client`) and the phase 2 Postgres
  server. Always give multi-word fields `column=snake_name`.
- `lakuna_client`: generated by Serverpod (models + client migrations).
- `packages/lakuna_domain`: pure Dart business rules (money, qty, ids, HLC,
  permissions, document numbers). No Flutter or Serverpod imports.
- `packages/lakuna_data`: `LakunaStore` / `SyncTx`. Every business write goes
  through `store.write((tx) => tx.insert(...))` so the sync outbox is written
  in the same transaction. Stock and balances are ledgers.
- `lakuna_flutter`: Flutter app, Forui (preset `conhcc`), official Flutter
  MVVM architecture (ChangeNotifier view models, repositories with fakes,
  `Command` + `Result`, `provider`, `go_router`), ARB i18n (id default, en).
  All assets must work offline.

Phase 1 runs fully on the device (no server needed). The server, its
built-in authentication (`lib/server.dart`) and sync endpoints are for phase
2; build multi-user backend features with Serverpod when that phase starts.

The server and Flutter app run under the Serverpod runner, a background process per server package. The user attaches to it with `serverpod start`. There is no need to check if the server is running: make the changes and call the `serverpod` MCP tools as needed. If the server is not running, an informative error message will be received from the MCP server. Then call `tail_runner_logs` to learn whether it is still starting or why it stopped. If nothing is running, start it with `serverpod runner start` in `lakuna_server`, which returns once the server is up and leaves it running for the user to attach to. If it fails, fix the cause it reports (a build error, a port held by another process, Docker) instead of retrying; only a `serverpod runner start` your shell killed on a timeout is run again, since the runner keeps starting. Flutter apps declared with `auto_launch` launch once the user attaches; launch any app before that with the MCP tool `spawn_flutter_app`. Leave the runner running, and run `serverpod runner stop` only when asked.

While running, the runner watches for file changes to run incremental code generation and hot reload both the server and the Flutter app. `serverpod runner status` prints its state and the server addresses, which are not always the configured ports when another Serverpod runner on the machine holds them.

Calling `serverpod generate` directly is not needed, but might be useful to troubleshoot when an incremental generation fails.

ALWAYS use the MCP server instead of the command line for the tasks below. The `serverpod runner` commands are the exception: they manage the stack itself. Use the MCP server to:

- `create_migration` and `apply_migrations` for database (after you change data models).
- `create_repair_migration` if the database has drifted out of sync with the migrations.
- `tail_server_logs` to read logs from the server.
- `tail_runner_logs` to read the output of the runner itself (code generation, compilation, Docker, raw server output). The only tool that also works while the server is starting or after it stopped.
- `tail_flutter_logs` to read the raw stdout/stderr of the Flutter app.
- `hot_reload` / `hot_restart` to reload or restart the server and the Flutter app. ALWAYS call `hot_restart` after doing changes in the Flutter app that may not work with normal hot reload (which is automatically applied).
- `spawn_flutter_app` to start a Flutter app declared under `serverpod: flutter_apps:` in the server `pubspec.yaml`.
- `get_flutter_app_dtd` (Dart tooling daemon) for connecting to the app through the `dart` MCP.

NEVER edit generated code. The server's `lib/src/generated/` directory and the whole `lakuna_client` package are rewritten by the code generator. Change the `.spy.yaml` models, the endpoints, or `lib/server.dart` instead.

Migrations are a narrow exception: the `migration.sql` of a generated migration MAY be edited by hand when the generated SQL would lose data — to add a data transformation, or to reach a destructive change through non-destructive steps. Never touch the other files in the migration directory, and keep the schema the SQL ends up with identical to `definition.sql` — new databases are created from that file and never run `migration.sql`.

Only when the MCP is not available or `serverpod runner start` cannot bring the server up, fall back to the CLI in the server package:

- `serverpod generate` to regenerate the client and the generated server code.
- `serverpod create-migration` after changing a model with a `table` (add `--force` for destructive changes). It only writes the migration; the runner applies pending migrations when it boots the server.

Tests need no Docker. `config/test.yaml` sets `database.dataPath`, so Serverpod starts and manages the test database (an embedded PostgreSQL) itself, and the project's `docker-compose.yaml` is not used for it. Just run `dart test` in the server package.

Checklist after doing changes, in this order:

- `dart analyze` (CLI) / `flutter analyze` in `lakuna_flutter`
- `dart format` (CLI)
- `flutter gen-l10n` in `lakuna_flutter` after editing ARB files (keys must exist in both `app_id.arb` and `app_en.arb`)
- `create_migration` and `apply_migrations` (MCP - only if necessary)
- Do `serverpod` MCP `hot_restart` if required (hot reload is done automatically). Will also hot restart Flutter app
- Run tests, if applicable (`dart test` in the server package, `packages/lakuna_domain`, `packages/lakuna_data`; `flutter test` in `lakuna_flutter`)
- Check `serverpod` MCP `tail_server_logs` and `tail_flutter_logs` for any issues.

If the user asks you to test the app:

1. Use `get_flutter_app_dtd` (`serverpod` MCP) to get the Flutter app's DTD
2. Pass the DTD to `connect_dart_tooling_daemon` (`dart` MCP) to connect to the app
3. Use `flutter_driver` (`dart` MCP) to navigate through the app

The app is launched from `lakuna_flutter/lib/driver.dart`, which starts the Flutter driver extension with text entry emulation turned off so the app stays usable by hand. To let the driver type, set `enableTextEntryEmulation: true` there and `hot_restart` the app.
